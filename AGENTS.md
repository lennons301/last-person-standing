# Last Person Standing

## Project Overview

Football survivor picks game — private games where friends pick teams each round, get eliminated if their pick doesn't win, last person standing takes the pot.

## Tech Stack

- **Framework:** Next.js 16 (App Router), React 19, TypeScript 5.7
- **Database:** Neon (serverless Postgres), local Postgres 17 via Docker for dev
- **ORM:** Drizzle with postgres.js driver
- **Auth:** Better Auth (email + password, database-backed sessions)
- **UI:** shadcn/ui + Tailwind CSS
- **Testing:** Vitest
- **Deployment:** Vercel (lhr1 region) — production: <https://last-person-standing.app> (custom domain since 2026-06-04; `last-person-standing-theta.vercel.app` 308-redirects to it for backwards compatibility)

## Key Conventions

- **Auth**: Session cached per-request via `getSession()`. Use `requireSession()` in Server Components/Actions that need auth — it redirects to `/login` if unauthenticated.
- **Route protection**: `proxy.ts` (Next.js 16 replacement for middleware) redirects unauthenticated requests. Public paths: `/login`, `/signup`, `/api/auth`.
- **Database**: No RLS — authorization enforced in TypeScript. All IDs are UUIDs. `numeric` columns (entry_fee, amounts) are strings in TypeScript for arbitrary precision.
- **Types**: Inferred from Drizzle schema via `$inferSelect` / `$inferInsert`. See `src/lib/types.ts`.
- **Game modes**: `classic` is the only **multi-round** mode — one pick per round, survive round to round, last person standing. `turbo` and `cup` are **single-round**: N confidence-ranked predictions in one gameweek/round, longest streak of correct picks wins (no eliminations-to-advance, no carry-over). `cup` is turbo plus a tier handicap + lives. See `docs/game-modes/` for the authoritative per-mode spec.
- **Joining a game**: **self-service entry closes the moment a game starts.** The rule is one pure function, `evaluateJoinability` (`src/lib/game/joinability.ts`) — a game is open for entry while it isn't completed, still sits on its own `starting_round_id`, and that round's deadline is in the future (a round with no deadline, e.g. WC knockouts pre-draw, stays open, the same way game creation treats it as a candidate). It reads the starting round rather than a status, because no status ever says "started": `active` is set at creation and never moves, and a state that had to be flipped would need a trigger to fire, so a missed trigger would leave a started game joinable. A game with no starting round recorded reads as closed — a game we can't place is not a game we can call unstarted, and the cost is a request to the admin rather than an entry fee taken for a game that is half over. Both the join route (`POST /api/games/[id]/join`) and the invite page read that one function, and the invite page for a started game says so and points at the admin instead of rendering a join button that 400s; its copy and the route's error codes come from the same `JOIN_BLOCKED_COPY` table so they can't drift. Past that point entry is an admin decision: the creator's add-player route (`POST /api/games/[id]/admin/add-player`) stays **completely unrestricted** and a test pins that — a friend joining a game at round 20 of 38 is a deliberate human act, and that is the shape it should take. Don't add a second gate: extend the pure function.
- **Pick views (classic and turbo)**: the picker has two — **Fixtures** (`FixtureRow` per match) and **Table** (`PickTable`: one row per pickable team, five columns — team, league position, form, next opponent, win chance — opening on position ascending). Which one a round opens on comes from `defaultPickView` (league → Table, knockout → Fixtures); with no standings behind the round the Table is hidden entirely, and `PickViewToggle` is the shared control between them. The board fits a 360px phone: no horizontal scroll and no pinned column, which is what played, points and goals came out for (goals live in the form sheet's home/away split, one tap from the form cell; points has nowhere else until the form-guide page). Its proportions are a declared decision, not a consequence of the widest cell: each column's share is a `<col>` width in `COLUMNS` (one pair per breakpoint, plus a set for the board turbo adds its rank column to), the team name truncates rather than widening its column, and layout stays `auto` so a column that genuinely can't shrink to its share still takes what it needs instead of spilling. Only team and win chance sort — form is three results and the opponent's name answers nothing. The two modes differ in what a row's tap does: classic passes `onSelect` (a row selects, and the shared `PickConfirmBar` commits it — a tap never writes, in either view), turbo passes `ranking` (a sixth column adds the team to the confidence set and carries its move/remove controls, and a ranked fixture's other row is marked with the call). Turbo's Table replaces its remaining-fixtures list only — the ranked list stays above it in both views, because it owns drag-reorder, the prediction change and the draw, which a board of teams can't express. The row shapes, the sort and its degradation rules are pure functions in `src/lib/game/pick-table-view.ts` — put ordering logic there, not in the component. The Table's position column comes from `team.league_position`, written by the same sync pass (`persistStandings`) that fills the rest of the standings line the form sheet reads. Neither view repeats what the player already knows: a pre-season fixture row shows its league position alone (no "No form yet" filler — the empty half beside a position already says the season has not started, and the Table keeps its own per-cell wording because a blank cell in a labelled column reads as a gap — tappable all the same, since the sheet carries a position, a season record, the next fixture's odds and the link to the form guide, none of which need a played match), and a used team's chip is the round's *short* label ("Used GW3"), with the long round name carried alongside it for assistive technology — `UsedRoundLabel` (`src/lib/game/pick-table-view.ts`) is the pair, built from `round-label` rather than from the provider's round name.
- **Player summary (`/me`)**: the signed-in player's own record. Private by construction — the route takes no parameters, the player comes from the session, and there is no share endpoint or OG image for it. All of its arithmetic is one pure builder, `buildMeSummaryView` (`src/lib/game/me-summary-view.ts`): plain rows (games entered, picks made) plus a season filter in, the whole page view model out, so `PlayerSummaryView` lays out figures it never computes and the page itself only fetches and renders. `getMeSummary` (`src/lib/game/me-summary-query.ts`) is the only row source; extend that pair rather than adding a second query or deriving figures in the component. Bucket rules the builder owns: a success is a win in any mode plus cup's draw; picks a life absorbed are out of both halves of the accuracy rate and carried as their own count; pending and void picks count nowhere; no-pick fallback picks count exactly as hand-made ones and are never flagged; games still in setup or open haven't been played yet, so the query leaves them out. Below the headline the page breaks down by mode — every mode gets a section (played, won, win rate, plus a sub-row per competition season), and a mode with no history in scope says so rather than rendering a record of noughts. What each mode adds is what that mode measures: classic's **depth** is the number of rounds the player held a pick in (never the elimination round, which a rebuy clears), best and average, counted over every classic game in scope because a round held is a fact the moment it's picked; turbo's and cup's **streak** (longest and average) is read from `resolveWipeout` (`src/lib/game-logic/auto-complete-tiebreakers.ts`) — the same function that decides those games — and there is no second streak implementation in the codebase. Consequences of that reuse, all pinned by tests: the streak counts from the rank the game restarted at (the lowest rank *any* player got right), only completed games feed it (an in-progress game can't move the average), a total wipeout is a streak of zero rather than a game left out, and whose picks resolve it follows each mode's own collector — turbo over the players still standing, cup over every player it ever had. Classic carries a second block below its depth, **round one** — the survivor player's own question about themselves: how often the opening pick came off, how many opening picks went down, and how many of those games they bought back into. Round one is **the round that game started at**, not the competition's gameweek one: game creation attaches a new game to the earliest still-pickable round, so a game created in November opens at gameweek 12 and gameweek 12 is the first hurdle its players are put to. `game.starting_round_id` remembers where it began — written once at creation and never moved, because `current_round_id` advances as the game goes on — and the query reads that round's number straight off it as `firstRoundNumber`, so a game nobody has picked in yet still has a round one. The engine agrees since #203: the settle exemption, both rebuy routes and the rebuy offer, the progress grid's marker and its `draw_exempt` rendering, the live projection, the hero's exemption state and the deadline lock's opening/second-round branches all resolve that same round through `src/lib/game/starting-round.ts` — `isGameStartingRound` for "is this the starting round?" and `resolveRoundAfterStarting` for what used to be called "round 2", the next round on the competition's sequence rather than `number + 1`. Put any new starting-round rule through that module; `round.number === 1` was the shortcut that gave a mid-season game no exemption and no possible rebuy however `allowRebuys` was set. A rebuy this block counts is therefore one the engine actually offered. The page says "opening round" throughout for the same reason. The survival rate is denominated on the classic games whose round-one pick **settled**, not on the classic games played, for the same reason the accuracy rate and the streaks are: a round one still awaiting kick-off and one a cancelled fixture voided are neither of them a hurdle the player has been put to, and a rate over games played would put a nought on the player for each. The rate is `null` until something settles and renders as a dash; `games` is kept beside it so the page can still say what the rate is over. The rebuy count is denominated only on the round-one exits in games that had rebuys switched **on**: playing on from a lost round one in a no-rebuys game is the starting-round exemption, not a rebuy, and can't be held against the player. The same exemption is why the count beside it is labelled by the pick and not by an exit ("Opening pick down"): where it applies, a lost round one doesn't eliminate, so calling it an exit would be untrue for exactly the games the rebuy denominator already refuses to hold against the player. The figure is every round-one pick that went down, in either configuration, which is what keeps `settled = survived + exits`. What identifies a rebuy is a pick in a later round *plus* an elimination round that is no longer round one — a rebuy clears `eliminated_round_id`, and classic accepts advance picks for non-current rounds and never deletes them, so the pick alone would read a round-3 pick locked in before the exit as a rebuy that never happened. No payment row is read anywhere in the block, which is what keeps it right for free games; the price is two knowing misses, both documented at `buildClassicRoundOne`. A player who rebought and then never picked again leaves no later pick to see, and the `missed_rebuy_pick` reason that would say so is only written when a second payment row exists. And a player who missed the deadline of their game's *own* round one, in a rebuys-on game, went out with no pick row at all — `processDeadlineLock` eliminates on that round and on the one after it without writing a fallback pick — which leaves that game outside the rate rather than in it as an exit. Since #203 those branches follow the game's own rounds rather than the competition's gameweeks one and two, so the hole is the same width for every rebuys-on game: no mid-season game escapes it by falling through to the auto-pick path any more. Reading the elimination round's *number* would catch the ones who stayed out but not the ones who bought back in (the rebuy clears the round), so it would trade a silent omission for a rebuy figure stating a nought against a player who did rebuy; the omission is the quieter error, and it stays until there is a pick-derived way to see the case. Below the mode sections sits the **Teams section**, one block per **competition family** and never a career-wide list: a World Cup team set and a league one are disjoint, so a single ranking over both would compare nothing. The grouping key is the stored `competition.family_key` (`src/lib/game/competition-family.ts`), so every season of a competition pools by construction — which is the point, since one season yields one to three picks per team — and the block's heading comes from `COMPETITION_FAMILY_NAMES` there rather than from a competition name (those carry a season). A competition with no family key stands alone under its own id; add a family's name to that table when you add the family. Each block carries the number of seasons it pooled, so the page states what pooled rather than claiming that something did. Ranking rules the builder owns: rate descending with no minimum sample, tiebreaking on pick volume (the larger sample is the better-evidenced record) then club name, so the order never follows row order; a pick a cup life absorbed is its own count on the row and out of *both* halves of the rate, because the rate answers whether the team delivered and the team still lost; a team whose every pick a life absorbed therefore has no rate and sinks below the ranked ones. The two ends split the ranking down the middle before either is capped at `ENDS_LENGTH`, so no team is ever both a best and a worst, no team on the family's best rate is ever listed among its worst (four sides on 100% and one on nothing has exactly one worst), and a family whose teams all share one rate has no worst end at all. The expansion lists every team. Each block carries its **own season control**, never a page-wide one: families count seasons in incompatible vocabularies (a league season reads "2025/26", a World Cup "2026"), so one control over both would offer seasons half the teams under it have never heard of. The selection lives in the URL, one search parameter per family (`/me?teams-premier-league=2025%2F26`, built and read by `teamSeasonQuery` / `parseTeamSeasonFilters` beside the builder), which is what keeps the page a server component with no client state and makes a narrowed block a link somebody can share. Rules the builder owns: the selection narrows that family's team records and nothing else — the career headline and every mode section stay all-time — a block's season options come off the family's whole history rather than the narrowed set (so the control can always be cleared, including from a season the player made no picks in, which is what a link from another player's history does), and block order follows each family's whole history too, so narrowing one block never shuffles the page. Last inside `PlayerSummaryView` is the **Money section** — a heading, and under it a fold that is **collapsed on load and remembers nothing between visits**: most players are down on this hobby, so the figure is one they ask for rather than one the page puts in front of them. The headline profit/loss and the per-game breakdown sit inside the *same* fold, because an open headline beside a separately-visible list of losses gives the number away to a player who never asked. The split is `MoneySection` (`src/components/me/money-section.tsx`, client, owns the fold state via `Disclosure`) over `MoneyPanel` (`src/components/me/money-panel.tsx`, pure presentation, knows nothing about being hidden) — which is what lets the gallery render the opened state. Money rules the builder owns: a **stake** is a payment row that is paid or claimed, exactly what `calculatePot` counts, so a player's profit/loss reconciles with the pot on every game page — which makes a rebuy an extra stake (it is an extra payment row) and a refunded row no stake at all, so a total-wipeout game nets to nought; **winnings** count *every* payout row with its status read nowhere, because nothing in the app ever advances a payout past `pending` and filtering on status would report every winner as zero; a **free game** has no money rows at all, so it contributes nothing and gets no row of its own (a row of noughts reads as a game that cost nothing and lost) while still counting as a game played — `freeGames` carries how many the list leaves out. The breakdown is ordered biggest loss first, name breaking a tie, and every amount is a fixed-2 string added up in whole pence. Closing the page, below `PlayerSummaryView` and the Money section alike, is the **Settings fold** (`src/components/me/settings-fold.tsx`), collapsed by default and outside the summary model entirely — a payment handle is a setting, not a figure, so it's read from the player's own user row in the page rather than put through `buildMeSummaryView`, and it renders below `PlayerSummaryView` rather than inside it. It hosts `PayMeEditor` (`src/components/game/pay-me-editor.tsx`), the same control the admin Payments panel renders, saving through the same owner-only `POST /api/me/payment-handle`: this is a second door onto one setting, and the reason it exists is that a player who has only ever *joined* games previously had nowhere to set the handle they'd be paid on. Keep it that way — there is one payment-handle control and one write path for it; if a third surface needs it, render that editor.

## Environment variables

**Pattern.** `.env.example` (committed) documents every env var the app reads with placeholder values that are sufficient for `pnpm build` and `pnpm test` to succeed. Real values come from one of three places depending on context:

- **Local dev:** `.env.local` (gitignored). Run `just env-init` once to copy from `.env.example`, then replace placeholders for whatever services you actually want to exercise.
- **Production:** Doppler `prd` config → synced automatically to Vercel Production env via the Doppler-Vercel integration. Never set Vercel Production env vars directly; always go via Doppler.
- **Preview:** Doppler `stg` config is the source of truth, but is **not auto-synced** (Doppler free tier caps the workspace at 5 syncs and the slot was sacrificed). After changing any Doppler `stg` value, run `just sync-preview-env` to push the change to Vercel Preview env. See `scripts/sync-preview-env.sh`.
- **GitHub Actions:** repo-level secrets, set via repo settings (separate from Doppler).

If a new env var is added, update `.env.example` AND this list. Routes that read env at module load (e.g., `verifySignatureAppRouter` for QStash) require non-empty placeholder values; that's the whole reason `.env.example` exists.

Variables:
- `DATABASE_URL` — Postgres connection string.
- `BETTER_AUTH_SECRET` — Better Auth session secret.
- `BETTER_AUTH_URL` — app URL used for cookie scope.
- `CRON_SECRET` — shared secret for GitHub Actions and Vercel cron auth.
- `FOOTBALL_DATA_API_KEY` — football-data.org API key (free tier).
- `ODDS_API_KEY` — the-odds-api.com API key (free tier). Bookmaker 1X2 prices, de-vigged into the indicative win-probabilities the pick selector shows. Read only by the daily-sync cron (`syncFixtureOdds`), one request per competition per run; odds for a round freeze at its deadline. Absent or empty means the refresh is skipped entirely and fixtures render no win-probability — never a zero. Provisioned via Doppler like every other secret (`prd` auto-syncs to Vercel Production; `stg` reaches Vercel Preview through `just sync-preview-env`, whose `KEYS` allow-list includes it).
- `QSTASH_TOKEN` — Upstash QStash client token.

## PL season rollover (annual verification ritual)

Every August, the Premier League season changes — 3 promoted teams replace 3 relegated ones. The rollover itself is **automatic**: the daily sync (a GitHub Actions workflow, `.github/workflows/daily-sync.yml`, scheduled 04:00 UTC — *not* a Vercel cron; FPL's Cloudflare blocks Vercel egress, so the workflow fetches the FPL payloads and POSTs them to `/api/cron/daily-sync`) detects the season via football-data's `currentSeason` cross-checked against FPL's GW1 deadline (`ensureCurrentPlSeasonCompetition`), creates "Premier League YYYY/YY", and archives the predecessor in one transaction — all before any sync writes. On detection failure it throws `SeasonDetectionError`: zero writes, a failed `cron_run` row, a red Actions job. It never guesses.

The human ritual is **verification only** — nothing to execute:

1. **Check the first August daily-sync runs are green**: `gh run list --workflow=daily-sync.yml`.
2. **Run the read-only inspector** (season-agnostic — it derives the expected season from the sources): `doppler run -p last-person-standing -c prd -- pnpm exec tsx scripts/repair/inspect-pl-rollover.ts`. It verifies the new competition (38 rounds / 380 fixtures / 20 teams), GW1 pairings against both FPL and football-data, team badge + external-id coverage, and that predecessor seasons stay archived and untouched. Exits non-zero on any failed check.
3. **Add colour entries for promoted clubs** in `src/lib/teams/colours.ts` if the inspector flags any team falling back to grey.
4. **Add odds-name entries for promoted clubs** in `ODDS_API_NAME_TO_SHORT_NAME` (`src/lib/game/sync-fixture-odds.ts`) — the-odds-api spells clubs in full ("Wolverhampton Wanderers") where FPL abbreviates ("Wolves"), and a club absent from that table loses its win-probability with no error. Both tables are supersets: add, don't replace. The signal is the daily-sync log line `[syncFixtureOdds] … unmatched market(s)` (also `odds.unmatched` in the cron's response); a unit test holds the table to `TEAM_COLOURS`'s coverage, so keeping the two in step keeps CI green.
5. **Confirm a GW1 game can be created** — the new competition's Gameweek 1 must be pickable (future deadline) in the game-creation flow.

Two failure modes need a human hand, and both fail loudly rather than corrupt:

- **`SeasonDetectionError`** (red run, zero writes): the sources disagree or one is missing data — investigate before anything else; do not hand-create the season.
- **`mergeFootballDataIds` team-coverage error** (`missing football-data IDs after merge: <list>`): a promoted club's FPL `short_name` and football-data `tla` disagree (as of 2025/26 only Nottingham Forest: FPL `NFO`, fd `NOT`). Add a one-line entry to `FPL_TO_FD_TLA` in `src/lib/game/bootstrap-competitions.ts`, deploy, and let the next sync run. Team gaps fail loudly because every team must be matchable for live scoring; fixture-level gaps are warn-only (rescheduled / late-published matches fill in on subsequent runs).

## Component preview gallery

`/preview` renders components against hand-built fixtures — no auth, no database, no live game. It's the review surface for UI work: `/preview/game-hero` covers the game page's top-of-page chrome — the identity bar, the stat line (including the pot disclosure and the unpaid notice) and every `GameHero` state × game mode — from descriptors shaped like `buildGameView`'s output, `/preview/live-scores` covers the on-demand live scores pop-out from hand-built live payloads (including live-window scenarios a database won't produce on demand), and `/preview/picks` covers the pick selector's shared `FixtureRow` — the nested planner context and the form-detail panel included. It is grouped: a shared-row section (the states any mode can put the row in, including a fixture with bookmaker win-probabilities and the same fixture unpriced), then one section per mode. Classic's group also carries the **Table view** (`PickTable`): the same round as a standings board, one row per pickable team, at full width and at both phone widths (375px and 360px — the board fits five columns with no horizontal scroll, so the narrow columns are where that is measured), in the states the board has to survive — fully priced, the phone worst case (a used-team chip under one name and a team with no form beside it), unpriced, partly priced (the case the sink-to-the-bottom sort rule exists for), a season start with nothing played, and used/restricted teams. Classic's sections carry the full `SideState` matrix in classic's own wording, and `ClassicPick` itself in each state the card moves through (no pick / selected / locked-collapsed / round-closed) — the card states are what make the hero de-duplication reviewable, since what matters there is the round name and deadline being *absent*. Cup's section is `CupPick` itself (nothing ranked / part-ranked / read-only), reviewing the same absence plus what cup gets from the shared row for nothing: it sources neither form nor league position — a cup team's form lives in its league, deferred to the FA-Cup effort — so the bottom bar stands down and the tier annotations carry the row. Turbo's sections cover its whole picker — the real `TurboPick`, in each state of its submission (nothing ranked / partially ranked / fully ranked / unsaved changes / season start with no form / opened on the Table view) — plus its ranked rows in isolation and the **Table view as a ranking board**: the same `PickTable` in the mode where a tap adds to the confidence set, at all three widths (its sixth column makes it the tightest the board gets), in the states that mode adds (nothing ranked, part-ranked including a draw call that marks both of a fixture's rows, ranked to the round's count, unpriced, read-only). A closing form-detail section covers the enriched tap-through sheet (`TeamFormPanel`) at both widths: the home/away venue split with goals for and against, and the full home/draw/away market — which arrives with the row rather than from the form query, so it renders while the form is still loading and survives a form failure, and is absent entirely for an unpriced fixture. `/preview/form-guide` covers the full form-guide page (`FormGuideView`) the sheet leads on to, in the five states the data can put it in: mid-season from a pick (position line, home/away splits, priced next fixture, head-to-head), opened from a badge with no opponent (no head-to-head section at all), early season (a two-point line, an unpriced next fixture, two teams who haven't met), opening weekend before this team has kicked off (a real position against the full table — "14th of 20", the state the position-line snapshot ships into on day one — with no line yet), and season start with nothing recorded — the state that proves each section says what it doesn't know rather than rendering blank. `/preview/me-summary` covers the player's own summary page (`PlayerSummaryView`) at full width and at 375px, in four states: a full history (the career headline, then all three mode sections populated — classic's rounds survived and its round one, which is where the rebought state is reviewed (two opening picks down, both of them in games that offered a rebuy, one of the two bought back into — so the rebuy figure is read against those two rather than against all four classic games, and the one that wasn't holds picks in later rounds all the same, advance picks locked in before the exit that the elimination round is what tells apart from a rebuy); ## Per-fixture settlement

The game lifecycle (pick → fixture finish → evaluate → eliminate → advance) is driven by `settleFixture` (`src/lib/game/settle.ts`). It's called from every place `fixture.status='finished'` is written: `/api/cron/poll-scores` (live observation) and `syncCompetition` (bootstrap + daily-sync mirror).

Round completion is **emergent** — a round is done when every fixture in it has been settled. There is no separate round-batched processing step.

Recovery surfaces (idempotent safety nets, in case the inline settle missed something):
1. Game-detail page SSR → `reconcileGameState(gameId)`.
2. `GET /api/games/[id]/live` → same.
3. Daily-sync cron → `reconcileAllActiveGames`.
4. Manual `POST /api/cron/process-rounds` → same.

Never add a fifth trigger path — extend an existing one. See `docs/game-modes/README.md` for the full settlement model + state machines.

## Pre-season standings (the opening table)

Until one of a competition's own fixtures has finished, the table `persistStandings` writes is **not** the source's. football-data answers a new season's standings filter with the *previous* season's final table right up to kick-off, so a faithful sync would put last season's positions and points on every pick surface and leave the promoted clubs — absent from that table — with no position at all (which auto-pick reads as worst in the league).

`openingTable` (`src/lib/game/bootstrap-competitions.ts`) derives the competition's own opening table instead: every club at zero, ordered by the league's tiebreak chain — points, goal difference, goals scored, club name — which at all-zero resolves to alphabetical, by *our* club names. From the first finished fixture onward the source table is written verbatim, so mid-season points deductions and every other provider correction stand. The switch is read from `fixture.status = 'finished'` within the competition, nothing else; it needs no repair script and no backfill, because each sync rewrites the whole table.

Two consequences worth knowing: pre-season, auto-pick's worst-placed fallback resolves to the alphabetically-last club in the round (stated in `pickLowestRankedUnusedTeam`), and the snapshot below records the opening table at `matchday: 0`.

## Standings snapshot

`standings_snapshot` records one row per (competition, team, matchday): the team's place in the official table, plus its W/D/L and points at that point. It's written by `recordStandingsSnapshot`, called from `persistStandings` (`src/lib/game/bootstrap-competitions.ts`) — the same adapter standings read that sets `team.leaguePosition`, so there's one provider request and no second cron. Don't add another writer; extend that funnel.

Three properties to keep in mind before building on it:

- **`matchday` is the team's own played count**, not the competition's round number. Postponements leave clubs on different game counts, and "position after N played" is the only x-axis that survives them. A team yet to play lands at `matchday: 0`.
- **The whole table is recorded, zero-played teams included** — the league always has all its members, so `getTableSize` counts a full table (and the guide can say "of 20") from the opening weekend, rather than a figure that climbs as the first fixtures are played. The `matchday: 0` row carries an alphabetical placeholder for position (the opening table's, pre-season; the source's own, once the season is underway), so **`getPositionLine` excludes it at read time**: the line starts at a team's first actual game and never plots the placeholder. Filter on read, not on write.
- **It accumulates from deployment onward. There is no backfill.** A competition already mid-season starts its line wherever the first post-deploy sync found it. Surfaces must render a short or empty series as the ordinary early state (see `PositionLine`), never as an error or a fabricated flat line.
- **`(competition, team, matchday)` is the upsert target**, so repeated syncs within one matchday refresh that point rather than duplicating it — the last read of the day is the settled one.

Its only consumer is the form guide's position line (`/competition/[competitionId]/team/[teamId]`, `src/lib/game/team-form-guide.ts`).

## Adding a new competition

Before merging a PR that introduces a new competition:

1. **Bootstrap path.** Add the competition to `bootstrapCompetitions`. Confirm `syncCompetition` runs end-to-end against the chosen adapter (FPL / football-data / manual).
2. **Live scoring.** If FPL-bootstrapped, confirm `mergeFootballDataIds` doesn't throw on the team set; add to `FPL_TO_FD_TLA` if any team-code mismatch surfaces. If football-data-native, no merge step.
3. **Cup-mode requirements.** If the competition supports `cup`, ensure every team has its tier marker (FIFA pot for WC; design a per-competition equivalent for new comps) and that game creation refuses to start a cup game with incomplete coverage. Cup-tier maths silently returns 0 for untagged teams — never let it ship without runtime validation.
4. **Smoke scenarios.** For every game mode supported on the new competition, add a scenario to `scripts/smoke/lifecycle.smoke.test.ts`. Each scenario must seed fixtures, write final scores directly, call `settleFixture` (or `liveFixture` + `getLivePayload` for projection cases), and assert the relevant state. Local: `just smoke`; CI runs it automatically.
5. **State-machine docs.** Update `docs/game-modes/` if the new competition introduces a state transition not already documented (e.g. group-stage → knockout boundary handling, mid-tournament auto-elimination).
